## 1. 问题

CUDA stream 的并行是"提交时的贴标签"还是"执行时的开线程"？
多流重叠在真实硬件上到底能省多少时间，收益被什么吃掉？

## 2. 实验结构（S1-S5）

| Section | 内容 | 实测 | 结论 |
| --- | --- | --- | --- |
| S1 锚点 | 400MB D2D copy / 4096³ matmul 单测 | copy 1.48ms（~540 GB/s）/ matmul 11.9~13.1ms | 量级对齐，两个锚点健康 |
| S2 单队列 | 9 copy + 1 matmul 全塞同一条流 | queued 25.4 vs sum 25.6（0.8%） | 同流保序 = 队列语义 |
| S3 双流失叠 | 9 copy(s1) ∥ 1 matmul(s2) | 总 22.2 vs serial 22.9，**加速仅 ~3%（理想 41%）** | 真重叠但收益被资源竞争吃掉 |
| S4 时钟 | 负载前后 P-state / SM / 显存时钟 | P8(300/405) → P2(1350→1890/6800) | 显存时钟二元跳变，SM 时钟连续爬坡；copy 负载也能拉 SM 时钟 |
| S5 分配阻塞 | GPU 繁忙时新建输出张量 | CPU 堵 29.6ms；`out=` 预分配版 0.17ms | cudaMalloc 隐式同步定罪 |

S3 细节：重叠窗口真实存在（event 交叉相减可定量），但 copy 被拖慢 60%+（1.5→2.4ms/个），matmul 仅慢 18%。

## 3. 关键概念（当日建立，易混点标注）

- **stream 是队列不是线程**：`with torch.cuda.stream(s)` 只设 thread-local 当前流；CPU 单线程顺序提交，GPU 侧按队列分发到不同硬件。并行 = 多队列 + 硬件独立 + 资源不抢。
- **同流保序与硬件无关**：copy engine 和 SM 是不同硬件，同一条流上仍严格串行。
- **默认流有 legacy 隐式同步**：与所有流互相等待——"多流不加速"的第一嫌疑。
- **易混点（当日纠错）**：S3 的 9 个 copy 是 **D2D（显存内部）**，与 matmul 共享的是 **HBM 显存带宽，不是 PCIe**。D2D 根本不经过 PCIe。若换成 H2D 拷贝，争的才是 PCIe，且 8 GB/s 的链路会先饿死 copy。
- **event 是 GPU 时间轴刻度**：所有计时先问"event 记在哪条流、等不等那条流"。

## 4. 三个隐藏同步点（异步语义三陷阱）

1. event 放在默认流上 → 测到的是 CPU 提交时间而非 GPU 执行时间（0.339ms 案）
2. 新建输出张量的分配在 GPU 繁忙时隐式同步，CPU 阻塞 29.6ms（S5）

- 复现关键：`torch.cuda.empty_cache()` 强制真实 cudaMalloc 路径，否则 allocator 缓存让阻塞偶发不复现

3. pageable 内存下 `non_blocking=True` 被静默忽略

- 140ms 那两次运行比 42ms 复现多出 ~100ms 的环境因素（邻居？深度冷态？）——未复现

## 7. 关键认识

1. stream 提供并行**可能性**，共享资源决定**实际收益**；重叠的账分两行算：理想下界 max(a,b)，再扣资源竞争
2. 异步编程的敌人是隐藏同步点
3. 假设被证伪是排查常规路径：时钟 H1 被 iter0 数据杀死后干净转向——证伪的实验比含糊的"证实"值钱
4. 仪器比直觉可靠，但仪器也会骗人：验仪器（event 在哪条流）、验变量（assert 验的是谁）、验环境（采样与负载同时）同等重要
